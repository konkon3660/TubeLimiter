# TubeLimiter v2 — 만든 것 요약

## 뭐가 바뀌었나

기존(레거시)은 "시간 넘으면 차단"만 하는 회피형 도구였음. 새 버전은 차단 로직은 유지하면서 그 위에 **계정 동기화 + 게임화(스트릭/XP/업적)** 를 얹음. 목적: 차단이 뚫려도 "꾸준히 지킨 기록"이 아까워서 안 보게 만들기.

## 핵심 기능

| 기능 | 설명 |
|---|---|
| 시청 제한 + 차단 | 일일/요일별 한도 설정, 넘으면 유튜브 페이지에 오버레이로 차단 |
| 집중 모드 | 정해진 시간 동안 한도와 무관하게 즉시 차단. 진짜 커밋먼트 장치가 되도록 활성 세션을 도중에 끄려면 하드코어 모드 해제처럼 10분 대기(요청 후 취소 가능)가 필요하고, 그동안에도 긴급 시청으로 우회할 수 없음. 단, 아직 시작 전인 "지연(분)" 예약을 취소하는 건 즉시 처리됨 — 시작한 적이 없으니 대기가 의미 없음 |
| 예약 차단 | 요일·시간대를 등록해두면 그 시간엔 한도와 무관하게 자동으로 차단(예: 매일 22:00~07:00). 집중 모드와 같은 급이라 긴급 시청으로 우회할 수 없고 화이트리스트도 통하지 않음. 옵션(안드로이드는 설정 화면)에서만 추가·수정·삭제할 수 있고, 팝업/홈 화면에는 활성 여부만 읽기 전용으로 표시 — 끄는 버튼을 따로 두지 않아 진짜 커밋먼트 장치로 남음. 4시 사용량 컷오프와 무관하게 실제 시계 기준으로 판정(상세는 [BACKEND.md](BACKEND.md)) |
| 긴급 시청 | 차단 상태에서 5분간 예외 허용(사용 한도·수동 차단·Shorts 한도에만 적용, 집중 모드·예약 차단은 우회 불가), 횟수는 일/주/월 단위로 리셋. 남용 방지로 한 번 쓰면 15초간 재요청 불가. 그동안 본 시간은 총 시청시간에 그대로 포함되지만, 스트릭 판정에서는 빼주고(스트릭은 안 끊김) 그날의 "완벽한 날" 자격만 잃는다. **남은 횟수는 기기별이 아니라 계정 단위** — PC에서 3회를 다 쓰면 폰에서도 0회다. 안 그러면 기기 하나 바꾸는 걸로 커밋먼트 장치가 무력화된다(리셋 주기가 주/월이면 그 버킷 전체를 합산, 상세는 [BACKEND.md](BACKEND.md)) |
| 화이트리스트 / Shorts 차단 | 특정 URL 제외, Shorts 항상 차단 옵션. 둘 다 화면 내용을 봐야 판정되므로 **브라우저 전용**. 화이트리스트 항목은 부분 문자열이 아니라 세 모양 중 하나로만 해석된다(`extension/src/lib/whitelist.js`): 호스트만 적으면 **정확 일치**(`music.youtube.com`), 경로를 적으면 호스트 일치 + 경로 **접두사**(구분자 경계, `youtube.com/@lecture`), 슬래시·점이 없는 낱말이면 채널/영상 토큰(`@lecture`, 영상 ID). 유튜브 본체 호스트(`youtube.com`·`m.youtube.com`·`youtu.be`·`youtube-nocookie.com`)와 `/`·`/watch`·`/shorts` 같은 전면 통과 값은 저장 자체가 거부되고, 그런 값이 이미 저장돼 있으면(옛 항목·다른 기기에서 동기화된 항목) **판정에서 조용히 무시하고 옵션 화면이 사유를 표시**한다. `music.youtube.com`은 일부러 허용 — 아래 "측정의 정의" 참고 |
| Shorts 전용 일일 한도 | 전체 한도와 별개로 Shorts에만 거는 일일 한도("전체는 2시간, Shorts는 10분"). 넘으면 Shorts 페이지만 막히고 일반 영상(/watch)은 남은 전체 한도만큼 계속 볼 수 있다. 전체 한도와 같은 급의 한도라 긴급 시청·화이트리스트로는 뚫리고 집중 모드·예약 차단은 못 뚫는다. 하드코어 모드에서는 전체 한도와 똑같이 **올리는 방향이 거부된다** — 안 막으면 Shorts 한도를 올리는 게 우회로가 된다. **브라우저 전용**(안드로이드는 앱 단위 감지라 Shorts 여부를 모름). 차단 우선순위 전체는 `extension/src/lib/blockDecision.js` 상단 주석과 [extension/README.md](../extension/README.md) 참고 |
| 하드코어 모드 | 켜져 있는 동안 **차단을 약화시키는 모든 설정 변경이 거부된다** — 한도(일일·요일별·Shorts) 상향, 화이트리스트 추가, 긴급 시청 횟수 상향과 리셋 주기 단축(`daily`가 `monthly`보다 느슨하다), Shorts 항상 차단 끄기, 예약 차단 삭제·비활성화·구간 축소. 반대로 **더 세게 만드는 변경은 그대로 허용**한다(한도 축소, 예약 차단 추가·확대, 화이트리스트 삭제) — 스스로를 더 옥죄려는 사람이 하드코어를 껐다 켜야 한다면 커밋먼트 장치가 커밋먼트를 방해하는 셈이다. 판정은 화면의 `disabled`가 아니라 **저장 직전 규칙**(`extension/src/lib/hardcoreLock.js`의 `findHardcoreViolations`)이라 낡은 옵션 탭도, 오프라인 저장 경로도 못 빠져나간다. 모드 자체를 끄는 건 별개 관문(1시간 쿨다운 + 스트릭 0 리셋)이라 여기서는 안 막는다. **지금은 확장만** — 안드로이드 설정 화면은 여전히 한도 입력만 `enabled = !limitsLocked`로 잠그고 긴급 횟수·예약 차단은 하드코어 중에도 편집된다([BACKEND.md](BACKEND.md)의 계약 절) |
| 계정 로그인 | 이메일 회원가입/로그인 (Supabase Auth) |
| 계정 전환 가드 | 기기가 "이 로컬 데이터는 누구 것인지"(`accountUserId`)를 적어두고, **다른 user_id가 로그인하면** 계정에서 온 로컬 값을 지운다 — 기록·한도 스냅샷·`settingsCache`·`daily_usage` 동기화 마커·긴급 버킷 캐시. 로그아웃은 여전히 진단 로그만 지운다(같은 계정으로 다시 들어오는 게 정상 경로이고, 로컬 전용 기록은 서버에서 되받아올 수 없다). 표식이 없는 기기는 아무것도 안 지운다 — 업데이트 한 번에 기록을 잃지 않게. 지금 걸려 있는 차단·집중 세션·이 기기의 남은 긴급 횟수는 전환에서도 남긴다(안 그러면 "다른 계정 로그인"이 탈출구가 된다). 목록은 `extension/src/lib/accountReset.js`가 원본이고 테스트로 고정. **지금은 확장만**(계약과 안드로이드 대응 상태는 [BACKEND.md](BACKEND.md)) |
| 오프라인 설정 편집 | 서버에 못 닿아도 설정을 바꿀 수 있다. "로그아웃"과 "서버 불통"을 구분해서(로컬 세션이 남아 있는데 조회가 실패 = 오프라인, 서버가 4xx나 PostgREST 코드로 **답을 하면** 세션이 죽은 것 = 로그아웃), 오프라인이면 `settingsCache` + 대기분(`pendingSettingsSync`)에 저장하고 차단 판정은 즉시 새 값을 쓴다. 서버가 살아나면 **대기분 push가 pull보다 우선**하고, 올라가는 건 대기분에 담긴 필드뿐이다(다른 기기가 바꾼 항목을 되돌리지 않게). 하드코어 관문은 온라인/오프라인 분기 **전에** 태우므로 "인터넷을 끊고 한도를 올린다"는 통하지 않는다. **지금은 확장만** |
| 클라우드 동기화 | 설정/스트릭/오늘 사용량을 서버(Supabase)에 저장 → 확장·안드로이드 여러 기기에서 같은 계정으로 로그인하면 공유됨. 오늘 사용량은 절대값 덮어쓰기가 아니라 델타 합산(`increment_daily_usage` RPC)이라 기기별 몫이 안 사라짐 — 상세는 [BACKEND.md](BACKEND.md) |
| 자동 스트릭 | 자정마다 그날 사용량이 한도 이내였는지 판정 → 성공하면 연속일수 +1, 실패하면 0으로 리셋. 판정에서 긴급 시청 시간은 빼고 보고(긴급 시청은 스트릭을 안 끊음), 한도를 넘는 순간이 든 마지막 정산 구간(최대 1분)은 측정 단위 때문에 생기는 초과라 봐준다 |
| 완벽한 날 | 긴급 시청을 한 번도 안 쓰고 한도를 지킨 날. 스트릭과 별도로 누적일수·연속기록을 세고(`perfect_days`, `current_perfect_streak`), 긴급 시청을 쓴 날엔 스트릭은 이어지지만 이쪽만 0으로 끊긴다 — 긴급 시청을 벌하지 않으면서도 "안 쓴 날"은 따로 보상하는 이원화 |
| XP / 레벨 | 그날 안 쓴 시간 10분당 1XP(무제한 설정이면 24시간 기준) + 스트릭을 이어간 날은 그날의 스트릭 일수만큼 + 완벽한 날이면 +10XP + 마일스톤 보너스(달성 일수 × 5). 마일스톤은 3·7·14·30·60·100·365일 스트릭과 7·30·100일 완벽 연속. 레벨은 코스메틱(색상/칭호)만 바꾸고 한도·긴급 시청 같은 실질 기능엔 영향 없음 |
| 업적 뱃지 | 스트릭 마일스톤(`streak_N`) + 완벽한 날 연속 마일스톤(`perfect_N`) 달성 시 자동 잠금 해제 |
| 대시보드 | 최근 28일 히트맵(완벽/성공/초과 3단계), 업적 뱃지, 사용시간 막대그래프(7·14·30일 기간 선택, 분/한도 대비 % 전환), 시간대별(0~23시) 이용 패턴 그래프. 히트맵·막대그래프는 로컬 기록과 서버 `daily_usage`를 날짜별 `max(로컬, 서버)`로 병합해 그린다 — 재설치하거나 두 번째 기기에서 로그인해도 비어 보이지 않게. 시간대별 그래프만 로컬 전용(서버에 시간대 단위 기록이 없음). 과거 날짜는 **그날 실제로 적용됐던 한도**로 판정한다(아래 참고). 서버 병합과 한도 스냅샷은 양쪽 클라이언트에 다 있다 — 안드로이드는 히트맵 셀에 툴팁을 못 달아 추정치를 외곽선 + 범례로 표시하는 것만 다르다([MOBILE_PLAN.md](MOBILE_PLAN.md) 대응표) |
| 그날의 한도 스냅샷 | 히트맵/막대그래프가 과거를 지금 설정으로 소급 판정하면, 한도를 30분→2시간으로 올리는 것만으로 예전 실패들이 한꺼번에 성공으로 바뀐다. 그래서 그날 적용된 한도를 날짜별로 남기고(확장 `limit_history`, 60일 보관) 그 값으로 판정한다. 스냅샷이 없는 날(이 기능 이전, 또는 다른 기기에서만 시청해 서버에만 있는 날 — 한도는 날짜별로 서버에 올라가지 않는다)만 현재 설정으로 근사 판정하고, 그런 날은 추정이라고 화면에 밝힌다. **스트릭 정산도 같은 스냅샷으로 한다** — 히트맵만 스냅샷을 쓰면 며칠 뒤 한도를 바꿨을 때 같은 날을 히트맵과 스트릭이 반대로 판정한다. 양쪽 클라이언트 공통 |
| 동기화 진단 로그 | 동기화·인증 실패를 기기 안에만 남기는 50건 링버퍼(확장은 옵션 페이지, 안드로이드는 설정 화면에 복사/지우기 버튼과 함께). 실패만 쌓고 성공은 시각만 갱신하며, 마지막 성공이 24시간을 넘으면 팝업/홈에 조용한 한 줄 경고가 뜬다. 외부 크래시 리포팅을 붙이지 않기로 했기 때문에 그 자리를 메우는 장치 — 서버로 올라가지 않고, 민감정보는 애초에 들어가지 않게 막는다(계약은 [BACKEND.md](BACKEND.md)) |
| 다국어 (한국어/영어) | 확장은 `extension/public/_locales/{ko,en}/messages.json` 258키 + `default_locale: ko`, 안드로이드는 `res/values/`(한국어) + `res/values-en/`. 문구를 추가할 땐 **양쪽 로케일에 다 넣어야** 하고, 판정 순수 함수는 문구 대신 키·enum을 돌려준다 — 상세는 [extension/README.md](../extension/README.md), [ANDROID_SETUP.md](ANDROID_SETUP.md) |

수동 활동 기록(운동/공부 입력) 없음 — 전부 자동 판정. 레거시 버전에 있던 "화면 캡처해서 공부/놀기 AI로 구분" 기능은 이번 버전에서 드롭함.

## 위협 모델 — 무엇을 상대로 한 커밋먼트인가

이 문서와 화면 문구는 "커밋먼트 장치"라는 말을 반복해서 쓴다. **무엇을 상대로 한 커밋먼트인지 적지 않으면 그 말은 과장이다.** 한 줄로 요약하면 이렇다:

> **마음먹고 우회하는 사람은 못 막는다. 무심코 열게 되는 관성을 막는다.**

세 단계로 나눠 적는다. 각 줄의 근거는 코드다. 3단계를 솔직히 적는 것이 이 절의 목적이고, 여기 있는 항목을 "언젠가 막을 것"으로 미루지 않는다 — 대부분은 플랫폼 제약이라 못 막는다.

### 1. 막는 것 — 무심코·관성적 접근

| 무엇 | 어떻게 |
|---|---|
| 한도 초과 후의 "한 편만 더" | 차단은 `*://*.youtube.com/*` 전 경로에 걸리고(`host_permissions`), content script가 오버레이를 띄운 뒤 **500ms 워치독**으로 `video.pause()`를 계속 건다(`extension/src/content/content.js`). 오버레이 DOM을 지워도 재생은 계속 멈춘다 |
| 습관적으로 주소창에 youtube를 치는 것 | 탭 URL이 바뀌는 즉시 판정이 다시 돌고(`chrome.tabs.onUpdated`), 안드로이드는 폴링이 유튜브·YouTube Kids의 foreground를 잡으면 오버레이를 띄운다(활성 5초 / 유휴 30초 주기라 **최대 그만큼 늦는다** — `UsageMonitorService`의 `POLL_ACTIVE_MILLIS`/`POLL_IDLE_MILLIS`, 실측된 적 없음) |
| 정해둔 시간대에 열게 되는 것 | 예약 차단은 팝업/홈에 **끄는 버튼 자체가 없고** 긴급 시청·화이트리스트로 안 뚫린다. 집중 모드 종료는 10분 대기 |
| 기기를 바꿔 횟수를 리필하는 것 | 긴급 시청 남은 횟수는 계정 단위 합산([BACKEND.md](BACKEND.md)) — 단, 아래 2·3단계의 단서가 붙는다 |

### 2. 마찰만 주는 것 — 의도하면 되지만 귀찮은 것

| 무엇 | 마찰의 크기 | 근거 |
|---|---|---|
| 한도·화이트리스트·예약 차단을 느슨하게 바꾸기 | **하드코어 모드가 켜져 있으면** 저장 자체가 거부되고, 풀려면 하드코어 해제(1시간 대기 + 스트릭 0 리셋)를 거쳐야 한다. 하드코어를 안 켰으면 마찰은 0이다 | `extension/src/lib/hardcoreLock.js`. 안드로이드는 아직 한도 입력만 잠근다 |
| 긴급 시청 남용 | 1회 5분, 재요청까지 15초, 횟수는 계정 단위. **15초는 억제력이 약하다** — 3회 연속 사용에 30초가 더 들 뿐이다 | `lib/emergency.js`의 `EMERGENCY_GRANT_COOLDOWN_MS = 15 * 1000` |
| 집중 모드 도중 탈출 | 10분 대기(취소 가능). 아직 시작 전인 "지연" 예약 취소는 즉시 | `lib/focusMode.js` |
| 로컬 저장소 직접 편집 | devtools로 `chrome.storage.local`을 고치면 차단 상태·남은 횟수를 바꿀 수 있다. 서버 값과 다음 동기화에서 어긋나지만 그 자리에서 막는 장치는 없다 | — |

### 3. 못 막는 것 — 설계상 불가능하거나 플랫폼이 허용하지 않는 것

| 무엇 | 왜 못 막나 |
|---|---|
| **확장 비활성화·삭제, 앱 삭제·권한 회수** | `chrome://extensions` 토글 한 번이면 하드코어 모드도 예약 차단도 관여하지 못한다. 확장이 자기 삭제를 막는 API는 없다. 안드로이드도 사용현황 접근·오버레이·배터리 최적화 예외 셋 중 하나만 꺼도 차단이 멈춘다 — 이제 그 사실을 홈 화면에 경고로 띄우지만(`diagnostics/MonitorHealth.kt`의 `monitorWarning`, 권한 상실 또는 2시간 무심박) **경고는 막는 장치가 아니다** |
| **다른 브라우저·다른 크롬 프로필** | 확장은 설치된 프로필 안에서만 산다. 새 프로필은 감시 대상이 아니고, 게다가 **한 번도 동기화된 적 없는 기기는 긴급 시청 횟수가 full로 시작한다**(`service-worker.js`의 `getEffectiveEmergencyUses`는 버킷 캐시가 없으면 로컬 카운터를 그대로 돌려준다 — 오프라인에서도 긴급 시청이 되게 하려는 설계의 대가다) |
| **폰 브라우저의 `m.youtube.com`** | `UsageStatsManager`가 주는 건 **패키지 이름과 전환 시각뿐이고 URL이 없다.** 크롬을 통째로 감시하면 유튜브를 1분도 안 봐도 브라우저를 켠 시간이 한도에서 깎인다. 접근성 서비스를 쓰면 URL을 볼 수 있지만 배터리를 이유로 배제했다([MOBILE_PLAN.md](MOBILE_PLAN.md)). 근거와 함께 `android/.../usage/WatchedPackages.kt` 주석에 적어뒀고, 온보딩에도 사실대로 표시한다 |
| **리패키지 클라이언트(ReVanced 등)·서드파티 프론트엔드** | 패키지 이름을 사용자가 정할 수 있어 열거가 불가능하다 |
| **다른 사이트에 임베드된 유튜브, `youtube-nocookie.com`** | `host_permissions`가 `*://*.youtube.com/*`뿐이라 트위터·레딧·블로그의 임베드 플레이어에는 content script가 아예 주입되지 않는다. 집계도 차단도 안 된다 |
| **로컬 시계 조작** | 모든 대기·쿨다운·하루 경계가 기기 시계 하나에 얹혀 있다. 확장은 `Date.now()`/`new Date()`, 안드로이드는 `System.currentTimeMillis()` + `ZoneId.systemDefault()`이고 **서버 시각과 대조하는 코드가 없다.** 시계를 1시간 앞으로 돌리면 하드코어 해제 쿨다운이 끝난다. 영향 범위: 하드코어 1시간, 집중 모드 10분 대기, 긴급 시청 5분/15초, 오전 4시 하루 경계, 스트릭 정산, 긴급 횟수 버킷 리셋, 예약 차단 시간대. 서버 시각을 도입하지 않기로 한 결정이며, 여행으로 시간대가 바뀔 때의 동작은 아직 아무도 확인하지 않았다([QA_REVIEW.md](QA_REVIEW.md) §8) |
| **DB 직접 수정 — 게임화 수치 위조** | 스트릭·XP·업적은 **클라이언트가 판정해 `streaks` 테이블에 push한다.** RLS는 "자기 행만 건드릴 수 있다"를 보장할 뿐 **"자기 행에 거짓말을 못 쓴다"를 보장하지 않는다.** anon key는 설계상 공개돼 있고 자기 세션 토큰은 devtools에서 꺼낼 수 있으므로 `xp: 999999`는 curl 한 줄이다. 이 제품의 가설이 "기록이 아까워서 안 본다"인 이상, 기록이 위조 가능하다는 사실은 적어둬야 한다 |

## 측정의 정의 — 무엇을 "시청 시간"으로 세는가

한도가 재는 물리량이 무엇인지는 **정의의 문제**이고, 지금 정의는 아래와 같다. 코드는 그대로 두고 문서에 명시하기로 한 결정이라, 이건 개선 후보가 아니라 **현재 동작**이다.

### 확장: 재생 중 + 탭 보임 + 창 포커스

세 조건이 **모두** 참인 구간만 깎인다.

- 재생 중: content script가 메인 플레이어(`video.html5-main-video`)만 보고 판정한다 — 썸네일 미리보기 `<video>`를 재생으로 오판하지 않으려고.
- 탭 보임: `document.visibilityState === 'visible'` (`extension/src/content/content.js`의 `currentPlaybackState`).
- 창 포커스: `service-worker.js`의 `if (!wasPlaying || !wasFocused) return;`.

**의도**는 잠수 방지다 — 틀어놓고 자리를 비운 시간까지 한도에서 깎으면 억울한 실패가 난다. **대가**는 이렇다:

- **PiP(사진 속 사진)로 빼면 원본 탭이 hidden이 되어 계속 무료다.**
- 다른 탭을 보며 듣는 백그라운드 오디오도 무료다.
- 듀얼 모니터에서 한쪽에 틀어놓고 다른 창에서 작업하면 창 포커스가 없어 0분이다.

즉 지금 한도는 "유튜브를 볼 수 있는 시간"이 아니라 **"유튜브 창을 최상단에 두고 보는 시간"**을 잰다. 가장 흔한 시청 형태 하나(옆에 틀어놓기)가 통째로 면제된다는 뜻이고, 이 대가를 알고 택한 정의다.

### 확장: 집계는 `/watch`·`/shorts`만, 차단은 유튜브 전 경로

`isTrackableYoutubeUrl`이 `youtube.com` + (`/watch` | `/shorts`)만 집계 대상으로 본다. 홈 피드 무한 스크롤, 검색 결과 훑기, 댓글 정독, 채널 탐색은 **전부 0분**이다. 반면 차단은 `*://*.youtube.com/*` 전체에 걸린다. 한도를 다 쓰면 피드도 막히지만, 한도를 **깎는** 것은 영상 재생뿐이다.

### `music.youtube.com`은 영상 한도를 깎는다

YouTube Music의 재생 URL에도 `/watch`가 들어가고 호스트가 `*.youtube.com`이라 위 규칙에 그대로 걸린다. **작업용 BGM을 유튜브 뮤직으로 들으면 영상 한도가 닳고, 한도를 다 쓰면 음악까지 차단된다.** 빼고 싶으면 화이트리스트에 `music.youtube.com`을 넣으면 된다 — 화이트리스트가 거부하는 "유튜브 본체 호스트" 목록에서 이 호스트만 일부러 빼놨다(`lib/whitelist.js`의 `FULL_YOUTUBE_HOSTS`). 안드로이드도 같은 결론으로 맞췄다: YouTube Music은 감시 대상에서 **기본 제외**이고 설정에서 켠다(`WatchedPackages.kt`).

### 안드로이드: 앱이 foreground면 재생 여부와 무관하게 깎인다

`UsageStatsManager`는 화면 내용을 모르므로 "유튜브 앱이 화면에 떠 있는 구간"을 그대로 센다. 영상을 정지해두고 앱만 켜둬도 깎이고(잠수 방지 없음), 반대로 화면을 끈 채 듣는 백그라운드 재생은 안 깎인다. 감시 대상은 YouTube와 YouTube Kids(항상) + YouTube Music(설정). 여러 앱을 오갈 때는 구간의 **합집합**이라 벽시계보다 더 깎이지 않는다.

**두 클라이언트가 같은 한도에 서로 다른 물리량을 더한다.** 이건 버그가 아니라 각 플랫폼이 볼 수 있는 것의 차이이고, 계약으로 [BACKEND.md](BACKEND.md)에 적어뒀다.

### 해상도와 손실

- **1분 알람 해상도**: 패키징된 확장에서 `chrome.alarms`의 최소 주기가 1분이라 최대 1분까지 초과 시청이 가능하다. 스트릭 판정은 이 1분을 봐준다(`TRACKING_TICK_GRACE_MS`). 한도가 10분인 사용자에겐 10% 오차다.
- **10분 초과 구간은 버린다**: `service-worker.js`의 `MAX_ELAPSED_MS = 10 * 60 * 1000`. 절전/최대 절전 복귀나 서비스워커 장시간 정지 뒤의 구간이 여기 걸려 **0으로 처리된다.** 손실은 항상 사용자에게 유리한 방향(덜 깎임)이고, 반대 방향 오차가 스트릭을 억울하게 끊는 것보다 낫다고 판단한 편향이다. 다만 **얼마나 자주 발생하는지는 아무도 모른다** — 세는 코드가 없다.

## 알려진 한계 — 데이터의 비가역성과 부재

측정과 별개로, 데이터 쪽에는 지금 해결되지 않은 세 가지가 있다. 고칠 계획의 유무와 무관하게 사실대로 적어둔다.

- **서버 사용량은 단조 증가만 하고 정정 경로가 없다.** `increment_daily_usage`는 음수 델타를 `greatest(x, 0)`으로 자른다(클램프 자체는 옳다 — 안 그러면 델타 하나로 그날을 지울 수 있다). 문제는 **한 번 부풀려 올라간 하루를 되돌릴 방법이 없다**는 것이다. 대시보드 병합이 날짜별 `max(로컬, 서버)`라 로컬을 고쳐도 반영되지 않는다. "그날 기록 재설정" 같은 사용자 조작은 없다.
- **로컬 전용 데이터는 날아가면 끝이고, 내보내기가 없다.** 시간대별(0~23시) 이용 패턴, `limit_history`(그날의 한도 스냅샷), `emergency_history`는 **서버에 없다.** 재설치·프로필 삭제·기기 교체 시 영구 소실이고, 그러면 히트맵은 "현재 설정 기준 추정"으로 떨어진다. 몇 달치 스트릭을 쌓게 만드는 제품이 그 기록의 백업 수단을 주지 않는다는 조합이다.
- **계정 없이는 못 쓴다.** 로컬 전용 모드가 없어서 한도를 30분에서 1시간으로 바꾸는 데에도 이메일 가입이 필요하다. 설치 직후 이탈 지점이자, 자기 통제 도구치고는 넓은 개인정보 표면이다.

Supabase가 pause되거나 네트워크가 끊겼을 때 설정을 못 바꾸던 문제는 **해결됐다** — 위 기능 표의 "오프라인 설정 편집" 참고. 다만 오프라인 편집분은 서버가 살아나면 그대로 올라가므로 **마지막 쓰기가 이긴다**(필드 단위 타임스탬프가 없어 다른 기기의 동시 변경을 알 방법이 없다).

```
TubeLimiter/
├── extension/              ← 크롬 확장 (PC 브라우저 + 유튜브 PWA 커버)

│   └── README.md            ← 처음 설정·빌드·i18n·진단 로그
├── android/                ← 네이티브 안드로이드 앱 (유튜브 앱 자체 차단). 계획: MOBILE_PLAN.md

├── .github/workflows/      ← CI (확장 lint+format+test, 안드로이드 ktlint+유닛 테스트+릴리스 빌드)
```

레거시(대회 제출) 버전은 저장소에서 제거됨 — 게임화 이전의 회피형 차단 로직만 있던 버전으로, 참고할 내용이 남아있지 않아 삭제.

## 백엔드(Supabase) 상태

Supabase 프로젝트는 이미 생성/연결되어 있음 — `schema.sql` 반영 완료, URL/anon key는 `extension/src/lib/config.js`와 `android/.../auth/SupabaseConfig.kt` 양쪽에 동일하게 박혀 있음 (같은 프로젝트를 두 클라이언트가 공유). 테이블 구조와 동기화 방식은 [BACKEND.md](BACKEND.md) 참고.

새로 이 프로젝트를 처음부터 세팅해야 하는 경우(예: 다른 Supabase 프로젝트로 옮길 때)만 아래가 필요:
1. supabase.com 프로젝트 생성 → SQL Editor에서 `extension/supabase/schema.sql` 실행.
2. 두 클라이언트의 config 파일(`extension/src/lib/config.js`, `android/app/src/main/java/com/tubelimiter/app/auth/SupabaseConfig.kt`)에 새 URL/anon key 반영.

확장 빌드/로드·패키징 절차는 [extension/README.md](../extension/README.md), 안드로이드 빌드/서명은 [ANDROID_SETUP.md](ANDROID_SETUP.md)(설계 배경은 [MOBILE_PLAN.md](MOBILE_PLAN.md)) 참고.

## CI

`.github/workflows/ci.yml`이 push(main)와 모든 PR에서 두 잡을 병렬로 돌린다.

- **확장**(Node 20): `npm ci` → `npm run lint` → `npm run format:check` → `npm test`. 포맷은 린트와 별개 게이트다 — 트리 전체가 Prettier에 맞춰진 뒤 CI 게이트로 승격했다.
- **안드로이드**(temurin JDK 25 + `platforms;android-37.0` 설치 후): `./gradlew ktlintCheck` → `testDebugUnitTest` → `assembleRelease`. 게이트마다 스텝을 나눠서 어느 게 깨졌는지 CI 로그에 바로 보이게 했고, 순서는 빠르고 잘 깨지는 것부터다. `ktlintCheck`는 `check`에 붙지 `test`에는 안 붙으므로 테스트만 돌리면 스타일 게이트가 통째로 빠지고, `assembleRelease`는 릴리스에서만 켜지는 R8 축소를 태워 `android/app/proguard-rules.pro`를 검증한다(디버그는 minify를 안 해서 절대 못 잡는다). CI엔 `keystore.properties`가 없으니 미서명 APK로 성공한다.

JDK 25는 `android/gradle/gradle-daemon-jvm.properties`의 `toolchainVersion=25`(데몬이 foojay에서 JDK를 자동으로 받지 않게 하는 핀)에 맞춘 것이지 컴파일 타깃이 아니다 — 모듈이 뱉는 바이트코드는 그대로 Java 17이다.

테스트 파일은 진작 있었는데 아무도 돌리지 않던 상태를 메우려고 붙였다.

**두 잡 모두 `main`에서 실제로 돌아 통과한 상태다.** 안드로이드 잡은 처음 두 번 깨졌고, 원인은 둘 다 SDK 설치 스텝이었다:

1. 손수 짠 sdkmanager 탐색 스크립트를 **직전 스텝이 방금 현재로 만든 JDK 25 아래에서** 돌렸다. cmdline-tools가 JDK 25를 지원한다는 보장이 없다. → `android-actions/setup-android`로 교체하고, 그 스텝을 JDK 설치 **앞**으로 옮겨 러너 기본 Java를 쓰게 했다(`eab4bbf`).
2. **`platforms;android-37`이라는 패키지가 존재하지 않는다.** 플랫폼 패키지는 마이너 버전제로 바뀌어 `37.0`/`37.1`/`37.2`가 별도 다운로드이고, `compileSdk = 37`은 `37.0`으로 해석된다. bare major를 요청하면 `Failed to find package`로 죽는다(`e79d8ed`). **SDK를 올릴 때 또 걸릴 함정이라** [ANDROID_SETUP.md](ANDROID_SETUP.md)에도 적어뒀다.

잡별 상세는 [extension/README.md](../extension/README.md), [ANDROID_SETUP.md](ANDROID_SETUP.md).

## 테스트가 보장하는 것과 아닌 것

`cd extension && npm test`는 지금 **345개**가 통과한다(`node:test`, 확장 `src/lib`의 순수 함수 대상). 안드로이드는 `./gradlew testDebugUnitTest`가 같은 성격의 유닛 테스트를 돈다.

**"테스트 N개 통과"는 판정 규칙이 스스로와 일치한다는 뜻이지, 제품이 동작한다는 근거가 아니다.** 이 저장소에서 실제로 깨질 만한 것들은 대부분 순수 함수가 아니라 그 사이의 배관에 있다.

이번 수정으로 **테스트가 생긴** 영역:

- 서비스워커 수명주기 — `extension/test/workerLifecycle.test.js` (죽은 content script 재주입 대상 고르기, 무응답 프로브를 "재생 아님"으로 접기)
- 계정 전환 — `extension/test/accountReset.test.js` (지우는 키/남기는 키 목록 고정, 전환 판정)
- 오프라인 편집 — `extension/test/offlineSettings.test.js` (로그아웃과 서버 불통 구분, 대기분 누적, push/pull 우선순위, 하드코어 관문이 오프라인 경로에도 걸리는지)
- 하드코어 잠금 범위 — `extension/test/hardcoreLock.test.js`, 화이트리스트 해석 — `extension/test/whitelist.test.js`
- 안드로이드 감시 대상 패키지 — `WatchedPackagesTest.kt`, 감시 사망 판정 — `MonitorHealthTest.kt`

**여전히 테스트가 하나도 없는** 영역:

- **계측 테스트(`androidTest`) — 디렉터리 자체가 없다.** 앱을 띄워 오버레이가 실제로 뜨는지 확인하는 테스트가 0개다.
- 오버레이 주입(확장 content script, 안드로이드 `BlockOverlay`)
- `UsageStatsManager` 정확도 — 보고 시간과 실제 시청 시간의 오차
- 두 기기 동기화 왕복 — [BACKEND.md](BACKEND.md)의 계약들은 **양쪽 순수 함수를 각각 테스트하는 방식으로만** 검증된다. 실제로 두 기기가 같은 계정에 붙어 델타를 주고받는 왕복은 한 번도 자동으로 돌지 않았다
- 포그라운드 서비스 생존, 권한 흐름, 부팅 복구, OEM 절전 정책 대응

실기기·실브라우저로만 확인할 수 있는 항목 16개는 [QA_REVIEW.md](QA_REVIEW.md) §8에 체크리스트로 모여 있다. **아직 아무도 확인하지 않았다** — 하나씩 확인할 때마다 그 문서가 아니라 여기와 [ANDROID_SETUP.md](ANDROID_SETUP.md)에 결과를 적는다.

## 여러 세션/에이전트가 동시에 이 저장소 작업할 때

Claude Code 세션을 여러 개(다른 창, 원격 등) 같은 저장소에 띄워두면 같은 파일을 동시에 저장하다 내용이 섞일 수 있음 — 실제로 한 번 발생: 두 세션이 동시에 `daily_usage` 동기화 기능을 독립적으로 구현하다 `schema.sql`에 같은 함수가 두 번 들어가고, `service-worker.js`에 네이밍이 다른 구현 두 개가 섞인 채로 저장된 적 있음. 파일이 "마지막으로 읽은 뒤 바뀌었다"는 경고가 뜨거나 빌드가 중복 선언 에러를 내면 다른 세션이 같은 파일을 건드리고 있다는 신호 — 큰 작업 시작 전엔 다른 세션이 열려 있는지 확인하고, 겹치는 게 보이면 어느 쪽 구현을 남길지 먼저 정리하고 진행할 것.

## Manifest V3 참고 메모 (진행하며 챙긴 것들)

- **manifest_version 3 필수.** `permissions`(storage/tabs/scripting/alarms 등 크롬 API 권한)와 `host_permissions`(외부 URL 접근 권한, 여긴 `*://*.youtube.com/*`만 사용)는 분리해서 선언.
- **서비스워커는 계속 안 살아있음.** 일정 시간 idle이면 꺼짐 → 상태를 전역 변수에만 두면 날아감. 그래서 `chrome.storage.local`을 진짜 상태 저장소로 쓰고, `setInterval` 대신 `chrome.alarms`(1분 주기)로 주기 작업을 예약함 — 알람은 서비스워커가 꺼져 있어도 브라우저가 깨워서 실행해줌.
- **컨텍스트 분리:** content script(유튜브 페이지, DOM 접근 가능)와 background/popup/options(DOM 없음, chrome.* API 다 씀)는 서로 다른 실행 환경. 서로 대화하려면 메시지 패싱만 가능:
  - background/popup → content: `chrome.tabs.sendMessage(tabId, msg)`
  - content → background: `chrome.runtime.sendMessage(msg)`
  - 수신: `chrome.runtime.onMessage.addListener(...)`
- **CSP 제약:** html에 `<script>...</script>` 인라인 코드 금지, 항상 외부 .js 파일로 분리. `eval`이나 CDN에서 원격 코드 불러오기도 금지 — 그래서 Supabase 클라이언트도 CDN이 아니라 esbuild로 미리 번들링해서 로컬 파일로 포함시킴.
